# Windows 正式签名准备与验证

日期：2026-10-21。工作起点 f100a2a，main 干净，无修改前备份提交，现有 HEAD 为回退点。用户选择“中国大陆个人、需要办理正式签名”，随后询问签名是否必要；已说明这是可选的对外分发步骤，不是运行或下载能力的前提。尚未选择供应商或提交申请。

## 环境与证书

Windows SDK 10.0.26100.0 x64 SignTool 可用，其微软 Authenticode 签名为 Valid，具有时间戳。首次受限上下文未枚举到代码签名证书，随后在实际用户上下文只读复核发现一张其他项目自签名开发证书，信任链为 UntrustedRoot；未复用该证书、未触及私钥或根信任。

个人申请渠道与当前限制见 [签名说明](../WINDOWS_SIGNING.md)。正式 CA 证书尚缺，项目安装器状态仍是 NotSigned。没有创建测试证书、购买、申请、上传证件或向签名服务发送项目产物。

## 实现与实测

新增独立的签名模块、每文件 signer、Inspect/Build/Verify 入口和本地检查。Tauri 签名配置在受控构建目录中按参数数组生成；配置和脚本不接收 PFX、密码或 PIN。新增私钥容器扩展名忽略规则。

`npm run signing:test` 通过 11 项（本机有既存自签名证书，故包括其拒绝用例）：脚本语法、缺证书拒绝、带凭据时间戳 URL 拒绝、自签名拒绝、真实微软签名验过、错误发布者拒绝、篡改已签名副本拒绝、未签名项目包拒绝、构建前失败且无目录/包变化、逐文件 signer 失败保留原文件、verify 非零退出码。

微软二进制与篡改副本均未执行；只检查签名。原 SignTool 保持 Valid。测试只修改项目忽略目录中的副本。早期严格模式检查发现空 EKU 列表不支持直接属性访问，已改为显式枚举，并重新通过全部检查。

`npm run signing:inspect` 报 certificate_ready=false，files_modified=false。原候选安装器 SHA-256 仍为 `0ec8ed8a2611f4f9a370169170e48c4b701b82be90b4ee799101b3226764fc4b`。前端 lint/typecheck/build 重新通过；本轮未改 Rust 核心或界面业务逻辑，无需将以前的 59 项核心测试冒充本轮签名证据。
